# Resources Js Components

## Selection listener must be document-scoped, not bound to the inline text span
`AlignableText.vue`'s `mouseup` handler is registered on `document` (via `onMounted`/`onUnmounted`), not via `@mouseup` on the inline `<span ref="containerEl">` itself. This was a real bug, not a style choice: a drag-select that ends in the thin sliver of space just past the last character of a line can release the pointer over the *parent* block (`elementFromPoint` confirmed this — the point lands on the wrapping `<div class="font-serif...">`, not on any element inside `containerEl`). Since that parent is not a descendant of `containerEl`, a listener scoped to the span never sees the event, and the selection is silently dropped — the "assign citation / align to image" popover just never appears, with no error.

The existing `containerEl.value.contains(anchorNode/focusNode)` guard already scopes a document-level listener correctly, so there's no precision lost by listening globally — only the previously-missing coverage restored. If this handler is ever refactored, keep it document-scoped; re-binding it to the local element will reintroduce the bug (reproduce by dragging to end a selection ~2px past a line's last character and checking whether the popover appears).

Since the always-edit redesign the same handler serves both worlds: while `editable` it emits `select` *without* clearing the live selection (it's normal editor selection the parent merely remembers for the toolbar buttons); read-only consumers (the edition page panes) keep the original emit-then-`removeAllRanges()` behavior. Keep that branch on `props.editable` — clearing the selection of an editable surface breaks type-over-selection.

**While `editable`, a mouseup does NOTHING at all unless the interaction began on the text** — since the live selection survives release, a stray mouseup (a toolbar click, a native `<select>` popup releasing over the page) would otherwise find that still-valid selection and re-emit it as freshly made, and the page closes any open menu for a fresh selection — so choosing a work dismissed the assign menu a second time, by a second mechanism. Both emission and dismissal share the origin gate.

**Dismissal is DECIDED by where the interaction began (mousedown on the text, `[data-non-text]` excluded) but EXECUTED only at mouseup** — `onContainerMousedown` records `interactionBeganOnText`; the mouseup handler emits `selection-cleared` only when that flag is set and no selection resulted. Three real bugs are pinned behind this exact split: (1) a collapsed-selection-at-mouseup heuristic cleared the remembered selection when clicking a toolbar button, because the stale caret still sat in the contenteditable; (2) a native `<select>` popup fires its closing mouseup at the pointer's position on the page UNDERNEATH the popup — the text — so choosing a work dismissed the assign menu mid-use; (3) clearing state at mousedown re-rendered the chunks and destroyed the DOM under the in-progress drag, breaking every selection made after the first. Release position is meaningless; interaction origin is not; and no reactive state may change between mousedown and mouseup.

**While `editable`, NEVER feed `selection-start`/`selection-end` props** — the witness page passes neither. The selection is a cut point in `chunks`, so any change to those props rebuilds the text DOM, and rebuilding the DOM destroys the browser's LIVE selection — the thing the editor is about to Ctrl+X, and the thing every remembered offset was measured against (fourth real bug in this family: the live selection died the instant it was made, invisibly to tests that only checked the remembered state and the styled highlight). While editable, the native selection IS the highlight; the page stores offsets for its toolbar buttons and renders nothing for them. The props remain for read-only consumers (edition panes, AddToEditionPanel), where a styled highlight and a styled highlight is the point and no live selection needs to survive.

**A read-only surface must render NO `contenteditable` attribute at all** — the container binds `:contenteditable="editable ? 'true' : undefined"`, never `false`. An explicit `contenteditable="false"` makes Firefox treat the element as a non-editable island and purge any selection inside it the moment the mouse releases (and refuse programmatic ones), so the add-text panel's selection vanished on release and nothing showed what "Add selection" would add (real bug). The absent attribute means the same thing without the island semantics.
